## 宿題

- 取り組んだレベル：基礎
- やったこと（変更したファイル・設定・処理、または設計した取得方法）：`app/config.py` の `RAG_TOP_K` を `5` から `2` に変更し、変更前後で `--trace` の結果を比較した。
- 比較した質問と、固定した条件（モデル・対象資料など）：質問は演習と同じ「第2回の説明では、LoRAは何を固定し何を学習しますか? QLoRAは何を加えますか?」、モデルは `gemini-3.5-flash-lite`、対象資料は `lec01-main`〜`lec03-main` で固定。
- 結果（変更前後の回答・根拠、`--trace`の出力、時間・トークン数・生成API推定費用など）：
  - 変更前（`RAG_TOP_K = 5`）：`search_materials({'query': 'LoRA QLoRA 固定 学習'})` を1回呼び出し、第2回 p.51, p.52 を根拠に回答。入力 3,027 tokens / 出力 185 tokens / 応答 2回 / 推定費用 $0.001371 / 時間 20.24秒（※503再試行あり）。
  - 変更後（`RAG_TOP_K = 2`）：同じ検索クエリで1回呼び出し、同じく第2回 p.51, p.52 を根拠に回答。入力 1,740 tokens / 出力 218 tokens / 応答 2回 / 推定費用 $0.001067 / 時間 2.23秒。
- 改善した例と、残る失敗・制約：上位2件に p.52 と p.51 が入っていたため、回答の正確さを落とさずに入力トークンを約3,000から1,740まで減らせた。ただ、2件しか取らない設定だと、検索の順位が少しずれたときや複数ページをまたぐ質問では必要なページが漏れるリスクがあると思った。
- 気づき・疑問：`RAG_TOP_K` を減らすだけで入力トークン数とコストが素直に下がることが確認できた。質問の難しさに合わせて件数を調整するのが大事そう。
